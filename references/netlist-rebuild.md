# 网表重建

网表 = 「位号 · 引脚 · 网络」的完整对应关系。重建分两条独立路径，互为交叉验证：

| 路径 | 来源 | 作用 |
|---|---|---|
| PCB 侧 | `PAD_NET` 记录 | 权威网表，反映实际布线 |
| 原理图侧 | 引脚坐标 + 导线几何 | 兜底与比对，能在 PCB 网表过期时发现问题 |

两侧一致 → 可信度高。不一致 → 先怀疑取错了记录版本，再怀疑设计本身。

## 一、PCB 侧：权威网表

### 1. 只认当前元件

PCB 文档里的 `COMPONENT` 有历史残留。判据只有一条：**有 `Designator` 属性的是当前元件**。
没有位号的是删除痕迹，必须整体剔除，连同它的 `PAD_NET`。

`build_netlist()` 会统计并报告剔除数量。若剔除数为 0 而焊盘数明显偏多，检查属性解析。

### 2. `PAD_NET` 取最大 ticket

id 形如 `["PAD_NET", 元件id, 焊盘号, 焊盘id]`，载荷 `padNet` 是网络名。

同一 `(元件, 焊盘)` 会存在多条记录，常见三种：

- 空 `padNet`：焊盘曾经悬空，后来才接上；
- 不同 `padNet`：改过网络；
- 不同 `焊盘id`：封装换过。

**只取 ticket 最大的那条。** 取错会得出"引脚悬空"的反向结论。

### 3. 焊盘号 → 引脚号

`PAD_NET` 第 4 个字段是**封装焊盘 id**，不是符号引脚 id。两者可能撞名却指向不同的脚，
拿它当键会得到错位一到两位的引脚号——这种错误在报告里表现为"网络整体错位"。

正确顺序：

1. 按**焊盘号**匹配符号引脚的 `Pin Number`（物理引脚号 = 封装焊盘号）；
2. 找不到同号引脚时，才用焊盘 id 兜底。

### 4. 符号链

PCB 元件通常只有 `Device`，没有 `Symbol`：

```
COMPONENT.Device → DEVICE 文档 META.attributes.Symbol → SYMBOL 文档 → PIN → Pin Number/Pin Name
```

漏掉这一跳，引脚号与引脚名会全空，两侧比对也就无法进行。

### 5. 位号重复

同一位号挂在多个元件上时，焊盘无法唯一归属。这类位号必须**整体排除比对**，
而不是"先到先得"——否则会凭空造出一堆网络错位。报告里按 🟠 单独列出。

## 二、原理图侧：几何重建

### 1. 元件与引脚

`COMPONENT` 的 `attrs.DeviceName` 是 JSON 字符串，里面才有器件 uuid：

```json
{"name":"C0603_L","source":"","uuid":"..."}
```

属性有两处来源，合并时以 `ATTR` 记录（`parentId` 指向元件）优先，`attrs` 内联兜底。

### 2. 导线

`WIRE` 是逻辑组（只有网络名，没有几何），几何在 `LINE` 图元上，用 `lineGroup` 关联。
只收 `lineGroup` 能对上 `WIRE` 的 `LINE`；其它 `LINE` 是图形装饰。

### 3. 连通性

并查集，节点是坐标点（`round 2`）。只认三种接触：

1. 点与点重合（±0.02）
2. 线段端点与端点重合
3. 点严格落在线段内部（`0.001 < t < 0.999`，EDA 的 junction 语义）

**不要**用 ±1 以上的容差做朴素最近点匹配，平行引线会被误短接。

### 4. 网络命名

两个来源：`WIRE` 的 `NET` 属性；`netflag` / `netport` 元件的 `Global Net Name`（或 `Name`）。

同名网络全局合并（这是跨页、跨区域连接的机制）。合并后同一集合出现两个不同名字时：

- 要么真短路；
- 要么历史残留线段还在。

两种都只能交人工判定，**不要自动二选一**。程序把它们记在 `conflicts` 里。

没有命名的网络给临时名 `N$n`，比对时跳过（临时名两侧不可能一致）。

## 三、两侧比对

按 `(位号, 引脚号)` 求交集，比较网络名。统计四类：

| 计数 | 含义 |
|---|---|
| 可比对 | 两侧都有且原理图侧有正式网名 |
| 不一致 | 逐条列出，需人工确认 |
| 未命名跳过 | 原理图侧是 `N$n`，按名比对无意义 |
| 重复位号 | PCB 内重复 / 跨页重复，整体排除 |

不一致的典型成因，按概率排序：

1. 网络在原理图里叫 `LCD_GND`，PCB 里叫 `GND`——重命名没同步；
2. PCB 是按旧版原理图布的，之后原理图改了；
3. 位号重复，比的其实不是同一颗；
4. 解析取错 ticket。

报告只陈述差异，不替用户判定成因。

## 四、两版工程 diff

### 1. 元素级

键 = `文档uuid | 类型 | id`，值 = 去掉易变字段后的载荷。比较得到
`added / removed / changed`。

### 2. 必须过滤的噪声

不过滤会得到几千条"改动"，真实变更通常个位数。

| 噪声 | 表现 |
|---|---|
| ticket / firstTicket | 全文件重编号 |
| client / updateTime / version | 换客户端或机器重存 |
| zIndex / dataType | 图层顺序、批处理重编号 |
| `ELE_PLACEHOLDER` | 保存时的占位元素重编号 |
| `LAYER_FILL` / `POURED` | 铺铜重灌 |

`epru_diff.strip_volatile()` 递归剔除上表字段；`NOISE_TYPES` 整类跳过。

**不做坐标容差过滤。** 元件坐标 ±10~20 mil 的微调会原样出现在 `changed` 里，
需要人工分辨是布局微动还是真的挪了位置；只差几个 mil 也算变更，不替用户判定。
`max` / `min` 这类字段同理不再剔除——它们可能是焊盘的真实几何尺寸，
剔掉会让"焊盘变小了"这种变更彻底消失。若确实需要按容差判定，
那属于字段级比较器的增强，另立任务，不要在 diff 里凭阈值猜。

### 3. 网表级

元素级 diff 只说明"记录变了"。要回答"电性变了没有"，必须重建两版网表后
按 `(位号, 焊盘号)` 逐行比对，输出新增 / 删除 / 换网。

### 4. 结论必须落到记录

任何"已修复"的结论都要给三元组证据，例如：

```
PAD_NET[U5, 13, e75] = GND，且 NO_CONNECT ...-e54 由 yes 变 no
```

拿不到记录级证据就写"记录显示有改动，是否修复需核实"。

## 五、DRC 与网表的关系

**DRC 通过 ≠ 电路正确。** DRC 只验证工程在工具自身模型下的自洽性：间距、短路、
未连网络。以下问题 DRC 全部看不出来：

- 地址选择线悬空（工具认为"未连网络"是允许的）
- 封装与料号不符（工具不查采购）
- 二极管 / 三极管极性反接
- 采样电阻接在错误的一侧
- 丝印值与 BOM 不符

报告里必须向用户点明这一点，不能把"已过 DRC"当成结论依据。
